## Behaviour worth knowing

- **Layout:** hero (mark, h1, interest/source/availability/preview chips), then either a "Plan confirmed" panel or a "Where this stands" panel, then "About this activity", then S7. Aside: G5, S6, S10. Follows the `Design.md` detail recipe, so no new CSS is needed.
- **Steps panel:** three rows (say you'd go, choose a time, organiser confirms) each marked Done, Next or Later (text, not colour alone), with the next action pointing at the right-hand panel. The confirm button appears only when `confirmationEntry.allowed` holds **and** the screen is live, signed in, activity available, no plan, plan check finished. Otherwise there is no disabled button: a line starts "Why you can't confirm yet:" with the reason.
- **Plan:** if a plan exists for this activity, shows the confirmed London time, meeting point and a primary "Open the plan" (`onOpenPlan(plan.id)`). It says that interest is not attendance and that MYT does not book anything. A plan whose `activityId` does not match is ignored (treated as not ready, confirmation blocked).
- **Re-checking props on every render:** write callbacks reach S6 and S7 (`onSetInterest`, `onSetVote`) only when the activity is `available`, the plan check is `ready` with no plan, all child `activityId`s match the activity, mode is `live` and a user is signed in. Otherwise they are `undefined`, S6 receives `activityAvailable: false` or `planExists: true` as appropriate, and S7/S10 are not shown for an unavailable activity (S7 stays visible read-only when a plan exists). If child ids do not match the activity, children are replaced by an "Updating" placeholder.
- **Unavailable activity:** warning banner, "Planning is closed", no steps, no S7, no S10, S6 gets `activityAvailable: false`. The details stay readable.
- **Loading, error, missing:** skeleton layout; error panel with Back; "This activity isn't available" with Back. Back always calls `onBack`.
- **Source and timing labels:** "Verified event", "Unverified" or "Demo activity idea" chip plus a note. Verified shows "Listed time" and the checked date and says it is not a booking. Other kinds show "Proposed time(s)" as a suggestion. Options not in `validFutureOptionIds` are marked "passed or not valid". Times are `Europe/London` and require an explicit offset. Cost shows "Price not listed" for null, "Free" for 0, "About £x" for estimates.
- **Original link:** only plain `https:` URLs without embedded credentials become a "View original listing" button (via S2's `ButtonLink`, new tab, `noopener noreferrer`). A stored link that fails the check is not shown and the page says so.
- **People:** viewers (G5 strip), interested people (S6's list) and going people are separate. S5 draws no counts and no people lists itself.

## Remaining limitations and requests

- **Going people are not on this screen.** `ActivityDetailProps` has no going list or count, so after confirmation S5 points to the plan page. If G1 wants "who's going" on the detail view, it needs an added prop (for example `goingPeople: Loadable<ParticipantSummary[]>`).
- **Narrow screens:** below 860px the aside stacks after the main column, so the interest action sits below About and the time vote. Possible S2 follow-up: an `order` rule for the aside at that width. Not needed for correctness.
- While the plan check is `loading` or `error`, interest and vote controls are withheld and confirmation is explained as paused. There is no retry control here because the contract has no retry callback for the plan; S1's page-level error handling covers retry.
- `onNavigate` and `activity` ids are not used for routing; back and open callbacks come from the parent as specified.
- Private time, cost and source helpers duplicate C1 to C3 and will drift if those change; replace them after import.
