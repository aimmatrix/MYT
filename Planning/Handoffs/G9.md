## Contract and usage

`useAsyncAction<Value, Args>(action, scopeKey?)` returns `{ state, run, clear, reset }`. Use one hook instance for each independent mutation, for example interest, vote, confirmation and attendance. `run(...args)` returns the repository's explicit `ActionResult` or `CreatePlanResult`, or `null` when that instance already has an action in flight. Pass a route/user-specific `scopeKey` so old state is cleared when the action context changes. `state` matches G1's `ActionState`: idle, pending, saved with local timestamp, or error with retry. A thrown rejection becomes a safe `io` error. Repository error codes are mapped to safe, specific text for the UI; path and raw exception details are not displayed. A failed result never enters saved state. An `existing` plan result leaves the hook idle; the caller opens that saved plan instead of announcing a newly created save.

Example for S1 composition:

```tsx
const interestAction = useAsyncAction(
  (status: "interested" | "withdrawn") => actions.setInterest(activityId, status),
  `${currentUser.id}:${activityId}:interest`,
);
<InterestPanel actionState={interestAction.state} onSetInterest={interestAction.run} {...otherProps} />
```

Adapt `run` where a screen requires a non-null callback result: a `null` means a duplicate click while pending and must not trigger a second write or a success message. The hook does not globally lock other action instances.

`Feedback({ kind, message, title?, actionLabel?, onAction? })` renders a themed notice. Failures use an alert; progress, success and warning use polite status announcements. Keep a notice at a stable location near its action. `ActionFeedback({ state, mode, successMessage? })` converts G1 state to copy: preview says nothing is saved, pending says saving on this device, success says saved on this device with sync still pending, and failure shows Retry. Screens that already render their own `ActionState` need not add a duplicate feedback notice.

`ErrorBoundary({ children, resetKey?, onRetry? })` catches render errors and shows a retry control. Changing `resetKey` clears the fallback. Retry remounts children and may call `onRetry`; it never deletes, repairs or overwrites files. Place it around route content, with route-specific `resetKey`.
