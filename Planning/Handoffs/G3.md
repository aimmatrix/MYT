## Delivered

- `useMytData(input: UseMytDataInput): MytViewModel` loads catalogs, session, profiles, plans and route-scoped interests, votes and attendance from G2’s repository.
- One `data/` watcher routes changed paths to affected slices, debounced by 150 ms. It also responds when a previously absent participant folder receives its first file. The effect cleans the watcher and timers on route, user, mode or repository change.
- Generation and per-slice revision checks discard late reads from old routes or superseded refreshes. Repository read results preserve malformed-record issues; a failed read remains an error rather than becoming an empty collection.
- Mutations use G2’s methods and refresh the affected slices after local success. A per-action pending set rejects duplicate clicks. `actions` is null in preview and when signed out. A save result confirms the local write only; it does not claim peer sync.

## Integration

S1 should instantiate the repository for the current user and pass the stable repository and `filePort` to `useMytData`, with `activityId` and `planId` from the route. Keep those objects stable across renders. G9 owns visual pending, saved and retry state and should wrap these callbacks. G4/T2/T4/T5 remain responsible for ranking, participant counts, consensus and eligibility; this hook exposes the source records and does not duplicate those rules.

Only the selected activity and plan are loaded in the respective maps. A feed needing interested counts for every activity requires a separate repository selector or explicit extension of the contract; it should not infer counts from an unloaded map. Reopening another activity triggers a scoped load.
